# SAT-Graph en IA Jurídica: trazabilidad del pipeline

**Objeto de estudio.** Implementación del commit `3e106be` en `v8`; ruta del chat con SAT sobre PostgreSQL. Las figuras son un mapa de la implementación, no una reproducción de FAIA ni de *A New Metadata-Aware Retrieval-Augmented Generation (RAG) Architecture for Trustworthy Legal Question Answering*. Esos diagramas sirvieron como referencias visuales de fases y niveles de detalle, no como evidencia de componentes implementados aquí.

## A. Preparación del corpus, fuera de la consulta

| Etapa | Entrada → salida | Código y decisiones |
|---|---|---|
| **A1 · Fuente** | PDF → archivo de entrada + identidad documental | [`main.py`](../../backend/main.py), [`ingestion/pipeline.py`](../../backend/ingestion/pipeline.py) (`process_single_pdf`). Diferenciar el documento original de su extracción y de la edición publicada. Un archivo disponible no implica elegibilidad para el chat. |
| **A2 · Conversión y evidencia** | PDF → Markdown + artefacto Docling → evidencia con hashes | [`ingestion/conversion.py`](../../backend/ingestion/conversion.py) (`convert_for_ingestion`), [`ingestion/docling_processor.py`](../../backend/ingestion/docling_processor.py) (`process_pdf_artifact`), [`ingestion/source_evidence.py`](../../backend/ingestion/source_evidence.py) (`persist_source_evidence`). Se preserva la identidad de los bytes; el hash no acredita por sí mismo vigencia jurídica. |
| **A3 · Estructura candidata** | Texto y estructura Docling → nodos, rangos, jerarquía y diagnósticos | [`ingestion/legal_structure.py`](../../backend/ingestion/legal_structure.py) (`parse_legal_structure`, `align_docling`), [`ingestion/sat_graph/store.py`](../../backend/ingestion/sat_graph/store.py) (`stage_document`, `stage`). Se proponen límites por estructura jurídica; errores de extracción y pertenencia pueden requerir revisión. No se toma un candidato sin revisar como evidencia normativa de chat. |
| **A4 · Revisión y publicación** | Borrador revisado → nueva revisión documental y versiones publicadas | [`services/sat_corpus_routes.py`](../../backend/services/sat_corpus_routes.py) (`publish`), [`services/sat_corpus.py`](../../backend/services/sat_corpus.py) (`validate_edition`, `replace_text`, `CorpusEditor.apply`). Se verifican rangos, jerarquía y revisión de partida; Markdown y estructura se publican conjuntamente. El historial editorial no equivale a una cadena de reformas legales. |
| **A5 · Persistencia** | Edición publicada → `Resource` → `Work` → `CTV` → `CLV` | [`ingestion/sat_graph/runtime.py`](../../backend/ingestion/sat_graph/runtime.py) (`runtime_sat_store`), [`ingestion/sat_graph/postgres.py`](../../backend/ingestion/sat_graph/postgres.py) (`_transaction`, `_reader`). Se preservan relaciones `has_part`, `contains_version` y `has_text`; la revisión de lectura cambia transaccionalmente con las escrituras del grafo. La rama de chat usa `contains_version` y `has_text`, no las relaciones editoriales completas. |

**Vía separada.** El repositorio contempla publicación con un manifiesto explícito (`SATGraphStore.review`, `ReviewManifest` en [`contracts.py`](../../backend/ingestion/sat_graph/contracts.py)). Puede aplicar acciones `enact`, `amend` o `repeal` con cierres y versiones de destino. Esto no convierte una corrección del revisor en una acción normativa ni significa que el chat recupere acciones. La [sección 3.5.1 del paper local](../2505.00039%20SAT-Graph.pdf#page=9) plantea la disposición causante, la CTV terminada cuando corresponda, la CTV producida cuando corresponda y una unidad de texto recuperable del evento. No se dibuja ese camino como operativo en el chat: la [guía de API](../../backend/services/sat_api.py) marca causalidad fuera del subconjunto soportado.

## B. Consulta, selección y generación

| Etapa | Entrada → salida | Código y decisiones |
|---|---|---|
| **B1 · Recepción** | Consulta + idioma + conversación → petición preparada | [`main.py`](../../backend/main.py) (`legal_query_stream`, `_prepare_query_context`), [`context/conversation_prompt.py`](../../backend/context/conversation_prompt.py) (`bounded_history`), [`services/legal_queries.py`](../../backend/services/legal_queries.py) (`answer_query`). El pipeline gestiona el estado del corpus y detecta si necesita traducir de quechua a español para la recuperación. |
| **B2 · Interpretación** | Texto actual + preguntas previas → norma, artículo, inciso, numeral y ambigüedad | [`retrieval/sat_citations.py`](../../backend/retrieval/sat_citations.py) (`references`, `with_prior_reference`, `match_article_heading`). Son reglas del código, no un planificador LLM ni un filtro vectorial. Las referencias abreviadas solo se expanden cuando se pueden desambiguar. |
| **B3 · Alcance y lectura** | Referencia y elegibilidad → snapshot de encabezados, rama, norma o grafo global | [`retrieval/sat_chat.py`](../../backend/retrieval/sat_chat.py) (`SATChatRetriever._search`, `_retriever_for`), [`ingestion/sat_graph/postgres.py`](../../backend/ingestion/sat_graph/postgres.py) (`chat_heading_snapshot`, `chat_article_snapshot`, `chat_snapshot`). El catálogo ligero no se usa como texto de evidencia. Si cambia la revisión entre la consulta de encabezados y la lectura de la rama, se vuelve a resolver sobre un snapshot fresco. Las preguntas generales sin un encabezado inequívoco conservan el respaldo global. |
| **B4 · Recuperación** | Snapshot + plan → lista de secciones y procedencia, o abstención | [`retrieval/sat_citations.py`](../../backend/retrieval/sat_citations.py) (`resolve_reference`) selecciona CTV/CLV de un destino exacto y comprueba listas cuando aplica. [`retrieval/sat.py`](../../backend/retrieval/sat.py) (`SearchPlan`, `eligible`, `search`) opera el respaldo léxico: BM25 de contenido y campos de metadatos, fusión RRF; no embeddings ni PPR en la ruta predeterminada del chat. Por defecto se usa la última versión almacenada elegible sin consultar el reloj; un corte explícitamente configurado tiene reglas distintas. Un empate de versiones no se resuelve por puntuación. |
| **B5 · Contexto** | Evidencia ordenada → secciones completas, deduplicadas y acotadas | [`retrieval/sat_chat.py`](../../backend/retrieval/sat_chat.py) (`_expand_ranked_component`, `query_with_rerank`) prepara la ruta léxica. Presupuesto de evidencia **24.000 bytes UTF-8** por defecto; no es el tamaño total del prompt ni una medida de tokens. La ruta exacta retorna su propia sección completa y aplica el presupuesto allí. |
| **B6 · Redacción** | Pregunta + contexto e instrucciones → borrador en español | [`services/legal_queries.py`](../../backend/services/legal_queries.py) (`answer_query`), [`context/context_engineering.py`](../../backend/context/context_engineering.py) (`build_legal_prompt`), [`context/prompt_templates.py`](../../backend/context/prompt_templates.py) (`build_prompt_for_cohere`), [`agents/pydantic_agents.py`](../../backend/agents/pydantic_agents.py) (`stream_general_text`, `respond_general`), [`services/cohere_chat.py`](../../backend/services/cohere_chat.py) (`chat_stream`, `chat`, `_record_usage`). El texto completo se envía en el contexto de generación; se evita repetir extractos en el prompt enriquecido. Si no hay evidencia, el pipeline no genera una orientación como si la hubiera. |

## C. Validación, citas y entrega

| Etapa | Entrada → salida | Código y decisiones |
|---|---|---|
| **C1 · Validación** | Borrador + documentos recuperados → respuesta validada e informe | [`modules/validation/services/response_validator.py`](../../backend/modules/validation/services/response_validator.py) (`validate`), [`cross_checker.py`](../../backend/modules/validation/services/cross_checker.py), [`self_correction.py`](../../backend/modules/validation/services/self_correction.py). Se puede disparar corrección; no es una prueba formal de fidelidad de todas las afirmaciones. [`services/legal_queries.py`](../../backend/services/legal_queries.py) (`_response_citations`, `_evidence_summary`) arma citas y evidencia; verifica por separado que norma y artículo en el texto no se hayan cruzado cuando se evalúe el sistema. |
| **C2 · Idioma de salida** | Respuesta validada → español o traducción quechua según modo | [`services/legal_queries.py`](../../backend/services/legal_queries.py), [`modules/language/services/translation_service.py`](../../backend/modules/language/services/translation_service.py). Cuando la traducción falla, se informa y puede conservarse el español; no se debe interpretar el texto del borrador como traducción validada. |
| **C3 · Protocolo y persistencia** | Deltas, estados y resultado → NDJSON e historial de conversación | [`services/legal_stream.py`](../../backend/services/legal_stream.py) (`stream_legal_query`), [`services/stream_guard.py`](../../backend/services/stream_guard.py) (`guard_stream`), [`models/stream_events.py`](../../backend/models/stream_events.py), [`main.py`](../../backend/main.py) (`_persist_assistant_response`). En español el usuario puede ver deltas **antes** de la validación; se persiste el resultado final antes de emitir `final` cuando aplica la persistencia. En modo quechua no se transmite el borrador español como texto en vivo. El contrato incluye `meta`, `stage`, `chunk`, `final` o `error`, y `done`. |

## Desglose para mantener el recuperador

**Qué se reutiliza y qué no.** El proceso puede reutilizar la vista PostgreSQL por identidad del almacén, alcance y revisión, el `SATRetriever` por identidad de snapshot, y la elegibilidad y los índices BM25 para una configuración compatible. `SATRetriever.search()` vuelve a puntuar cada consulta. [`SATChatRetriever.get_cache_revision()`](../../backend/retrieval/sat_chat.py#L107) devuelve `None`, así que [`_prepare_query_context()`](../../backend/main.py#L145) no habilita la caché de respuesta final para este camino. Una respuesta más rápida en una ejecución caliente no implica que se haya reutilizado texto de Cohere.

**`_search()`** mezcla cuatro responsabilidades: (1) analizar e heredar referencias; (2) elegir estrategia de lectura y controlar revisiones; (3) resolver referencias exactas, encabezados y pedidos ambiguos; (4) ejecutar ranking y componer su salida. En una refactorización posterior convendría extraer únicamente tres operaciones con fronteras claras: *planificar alcance*, *leer snapshot coherente* y *resolver o buscar*. Primero fijar el comportamiento con pruebas que discriminen ruta exacta, rama con cambio de revisión, respaldo global y abstención. No cambiar el ranking junto al refactor.

**`_expand_ranked_component()`** toma resultados del ranking, relaciona el hit con su CTV elegible y su CLV, y comprueba que cada descendiente elegible pertenezca al mismo recurso y coincida por rango y texto. No reconstruye el artículo sumando incisos. Excluye solapamientos jerárquicos, verifica el presupuesto en orden de ranking, genera rango e identidad coherentes con la evidencia completa y conserva el motivo de omisión. Si el candidato principal es inconsistente o no cabe, se abstiene; para un candidato posterior, sigue con el resto. Un refactor acotado puede separar *verificar una unidad* de *seleccionar unidades bajo presupuesto*, dejando el formato de respuesta aparte solo si se reutiliza.

## Cuatro trazas observadas en PostgreSQL local

Se instrumentaron las llamadas de lectura del recuperador usando el almacén normal, **sin modificar el backend**. Cada caso usó `top_k=5`, hasta 30 candidatos, sin historial ni corte temporal explícito. No se llamó a Cohere. Los nodos corresponden al tamaño del snapshot que se devuelve al recuperador, **no a lecturas físicas de disco**. El proceso se reutilizó entre casos, por lo que una llamada al almacén puede acertar en caché. Los bytes son la suma de la evidencia seleccionada, no el tamaño del prompt ni el número de tokens.

| Pregunta | Qué se leyó | Resultado observado |
|---|---|---|
| «¿Cuáles son las reglas para una audiencia única en un proceso de demanda de pensión de alimentos?» | Catálogo de encabezados (6.879 nodos/2.641 aristas) → rama (39 nodos/25 aristas). | Un resultado, **1.541 bytes**. `Ley 31464 → Art. 3 incorporador → Art. 170-A`. No se atribuye el número 170-A como un artículo propio de la ley incorporadora. |
| «En el artículo 8 de la Ley 30364, ¿cuáles son los cuatro supuestos del inciso d)?» | Catálogo → rama (40 nodos/25 aristas). | Un resultado, **812 bytes**. `Ley 30364 → Art. 8 → Inciso d)`; no retorna los cuatro tipos del artículo completo. La traza es de recuperación, no verifica qué enumeraría el modelo. |
| «El papá de mi hija dejó de pasarme dinero y no sé dónde trabaja. ¿Puedo pedir alimentos y qué necesito?» | Catálogo → snapshot global (23.666 nodos/18.446 aristas). | 30 candidatos, hasta 5 hits para el empaquetado, 4 evidencias finales, **7.139 bytes**. Se registró `structural_overlap`. |
| «Dame los literales.» | Catálogo → snapshot global. | `abstain` / `unresolved_reference`, sin ranking, **0 bytes**. La guarda se ejecutó después de obtener la vista global. |

**Qué no prueba la integridad estructural.** La búsqueda cotidiana trajo el artículo 164-A, dos unidades del DL 1377 con la misma etiqueta pero CTV y rangos distintos, y el artículo 22 del Código de los Niños y Adolescentes sobre trabajo adolescente. **No** recuperó el artículo 96 sobre competencia. El presupuesto y la deduplicación por jerarquía no sustituyen una evaluación de pertinencia.

**Qué contiene la traza.** [JSON observado](trazas-locales.json): operación, alcance, cantidad de nodos y aristas, referencia, orden de hits, CTV, offsets cuando el recuperador los emite y SHA-256 calculado por el arnés sobre el texto devuelto. La ruta exacta incluye una ruta de cita; no emite `start` ni `end` en el hit. La ruta léxica sí comunica offsets. Reejecutar desde la raíz con `uv run --no-sync python -B docs/sat-architecture/trazar_recuperacion.py` y un PostgreSQL local con el corpus publicado. Los identificadores y tamaños pueden variar al publicar una nueva edición.

## Protocolo para reportar esta implementación en un paper

1. **Congelar datos y variantes.** Registrar commit, revisión o hash del corpus, política temporal, tamaños de búsqueda y modelo/configuración. Medir el efecto de código con el mismo corpus; medir por separado el efecto de una corrección documental. No describir el contraste con otro motor como algorítmico si el corpus es distinto.
2. **Separar las unidades de evaluación.** Para ingesta: cobertura y estructura (segmentos faltantes, límites y padres correctos); para recuperación: Recall@k, Precision@k, MRR/nDCG sobre secciones de referencia; para generación: atribución norma/artículo, condiciones, plazos y exhaustividad. Para una futura ruta causal: F1 de atribución de acciones y completitud de las cadenas, con casos anotados.
3. **Medir por fase.** Latencia de recuperación, primer delta y entrega final por separado. Distinguir primer uso con proceso nuevo, proceso caliente y almacenamiento realmente frío. Medir bytes de evidencia y `billed_units` de Cohere por separado. Publicar distribución y número de repeticiones; una sola pregunta sirve como traza de diagnóstico, no como conclusión general.
4. **Comparar baselines y ablaciones.** Usar búsqueda plana y SAT con/sin resolución estructural y con/sin empaquetado. Medir caché por separado con evidencia idéntica. Para preguntas amplias y ambiguas, contabilizar abstenciones justificadas, fallos de recuperación y citas equivocadas, no solo mejoras de latencia.
